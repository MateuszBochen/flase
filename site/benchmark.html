Speed of Flase compared with web database tools

Measured 23 November 2026 · Flase 0.12.1

How long does it take from a click on a table (or running a query) until the rows are on the screen? Five web database clients were measured in the same browser, against the same MariaDB and PostgreSQL tables, on the same computer.

What was measured

Every run starts a new browser context, logs in and opens the tool at the database with the list of its tables - this part is not measured. Then one action is measured until all its rows are rendered, plus two more frames so the rows are really painted:

Open table
Click on table wide_test (50 columns of texts, numbers, dates and long texts, 1000 rows) in the list of tables - the tool shows its first 100 rows.
Table with 20 foreign keys
The same with table fk_test: 24 columns, 20 of them are foreign keys to 20 other tables (ref_01 … ref_20), 1000 rows. Tools which show links or values of referenced rows have more work here.
SQL query
SELECT * FROM wide_test LIMIT 1000 typed into the SQL editor of the tool and run - until all 1000 rows are rendered (shown).

For each action these values were recorded:

Time to rendered rows
Wall clock time from the click to the second frame after all rows are on the page - what the user waits for.
CPU time of page
Time the browser's main thread was busy (JavaScript, style, layout, paint) during the action - Chrome TaskDuration.
DOM elements
Elements on the whole page after the action - a large page is slow to scroll, resize and change.
JS heap after GC
Memory of JavaScript of the page after garbage collection.
Data received
Bytes received from the server during the action (HTTP and WebSocket).

The first run of every tool and test only warms up caches of the tool and of the database and is not counted; the result is the median of the next 7 runs.

AMD Ryzen 5 3600 (6 cores), 64 GB RAM, Linux - all tools, databases and the browser on the same machine, so network latency is not part of the results.
Browser
Chromium 131 (Playwright 1.49.1, headless), window 1920 × 1080.
Databases
MariaDB 11.4.13 and PostgreSQL 17.11 in Docker, the same tables in both.

Production Docker image (docker/production/Dockerfile), default settings (100 rows per page).

Official Docker image (PHP 8.3, Apache), $cfg['MaxRows'] = 100 so it shows the same 100 rows.
Adminer 6.3.0
Official Docker image. It shows 50 rows by default; the table is opened with limit=100, which is the same page as other tools.
pgAdmin 4 9.18
Official Docker image (desktop mode). Table is opened by View/Edit Data → First 100 Rows, SQL in Query Tool (F5).
CloudBeaver 26.2.5
Official Docker image (web version of DBeaver). Default page of 200 rows changed to 100 (resultset.maxrows); for the SQL test fetch size of the result is set to 1000 before the measured run.

Notes

  • Adminer is a single PHP file which returns a plain HTML page without a JavaScript grid. For one page of 100 rows this is very fast - every action loads a new page, so state (open tabs, scroll, unsaved changes) is not kept between actions.
  • phpMyAdmin builds the whole HTML table and its JavaScript goes through every cell, so its time grows with every row: 1000 rows take seconds.
  • pgAdmin and CloudBeaver are full applications in the browser (React) - opening data opens a new panel with its editor and grid, which is most of their time of opening a table. Both have a virtual grid, so the query of 1000 rows in an already opened Query Tool of pgAdmin is fast. The grid of pgAdmin is in an iframe; its DOM elements are counted for the main page only.
  • Flase renders only rows and columns visible on the screen, so the page stays small for 100 and for 1000 rows. It sends rows as JSON over WebSocket - more bytes than compressed HTML, but no layout of a huge table. Values of referenced rows (labels of foreign keys) are loaded after the rows are shown.
  • Times include the work of the server of each tool and of the database; all of them ran on the same machine at the same time, each tool was measured in turn.

Run it yourself

The script and description of all containers are in the repository: tests/ui/bench-tools.js. With the tools running on ports 3010 (Flase), 8090 (phpMyAdmin), 8091 (Adminer), 8092 (pgAdmin) and 8093 (CloudBeaver):

docker run --rm --network host -v $PWD/tests/ui:/pw -w /pw \
  mcr.microsoft.com/playwright:v1.49.1-noble node bench-tools.js 7
